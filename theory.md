# Теоретический разбор проекта

Этот документ содержит подробное описание архитектуры, ключевых концепций и алгоритмов, использованных в проекте.

## 🏛️ Архитектура и ключевые концепции

### Объектно-ориентированное программирование (ООП)

Проект полностью построен на принципах ООП.

1.  **Инкапсуляция:** Данные классов (`Pipe`, `CS`) объявлены в `private` секции. Доступ к ним происходит только через `public` методы (геттеры и сеттеры). Это защищает данные от некорректного изменения и делает код надежным.

2.  **Абстракция:** Пользователю `Manager`'а не нужно знать, как именно хранятся трубы и станции. Он просто вызывает методы вроде `manager.addPipe()`. Классы предоставляют простой интерфейс для сложных действий.

### Архитектурный паттерн "Менеджер" (Controller)

Класс `Manager` выполняет роль центрального контроллера. Он изолирует логику управления данными от логики пользовательского интерфейса (`main.cpp`). Это классический пример **разделения ответственности** (Separation of Concerns): `main` отвечает за "показать и спросить", а `Manager` — за "обработать и выполнить".

### Хранение данных: `std::map` вместо `std::vector`

В последней версии проекта для хранения объектов `Pipe` и `CS` используется `std::map<int, T>` вместо `std::vector<T>`. Ключом в `map` выступает уникальный `id` объекта.

*   **Преимущества `std::map`:**
    *   **Быстрый доступ по ключу:** Операции поиска, редактирования и удаления объекта по его `id` выполняются за логарифмическое время `O(log N)`, что значительно быстрее, чем линейный поиск `O(N)` в `vector`.
    *   **Упрощение кода:** Больше не нужно искать индекс элемента перед его изменением или удалением. Мы можем напрямую обратиться к элементу `map.at(id)`.
    *   **Автоматическая уникальность ключей:** `std::map` не допускает дублирования ключей, что дополнительно гарантирует уникальность `id`.

### Система валидации ввода

Вместо множества функций для проверки ввода используется единая **шаблонная функция** `getValidInput<T>`. Она считывает всю строку целиком (`std::getline`), а затем использует `std::stringstream` для попытки преобразовать эту строку в нужный тип. Это защищает программу от некорректного ввода и падений.

### Сохранение и загрузка данных (Персистентность)

Выбран простой и надежный текстовый формат. Для каждого набора объектов сначала сохраняется их количество, а затем данные каждого объекта записываются **построчно**. При сохранении КС также сохраняется информация о ее исходящих соединениях, что позволяет полностью восстановить структуру графа при загрузке.

### Логирование

Класс `Logger` отвечает за запись всех действий в файл `log.txt`. Это стандартный инструмент для отладки и анализа работы программы.

## 🌐 Сетевые операции и графовые алгоритмы

Третья лабораторная работа ввела в проект концепцию газотранспортной сети, которая представляет собой **ориентированный граф**. Вершинами графа являются компрессорные станции (КС), а ребрами — трубы.

### Представление графа

Граф представлен с помощью **списков смежности**. В классе `CS` было добавлено поле:

```cpp
std::map<int, int> outgoing_connections;
```

Это `map`, где:
*   **ключ (`int`)** — это `id` компрессорной станции, в которую ведет ребро (труба).
*   **значение (`int`)** — это `id` самой трубы, которая соединяет эти две станции.

Такая структура позволяет для любой КС быстро получить список всех станций, в которые из нее ведут трубы.

### Соединение станций (`connect_stations`)

Этот метод реализует логику добавления нового ребра в граф. Алгоритм следующий:

1.  Запрашиваются ID исходной и конечной КС, а также диаметр трубы.
2.  Проводятся проверки: существуют ли такие КС, не совпадают ли ID, не соединены ли уже эти станции.
3.  Происходит поиск **свободной** трубы (`is_used == false`) с заданным диаметром.
4.  Если труба найдена:
    *   Она помечается как используемая (`is_used = true`).
    *   В исходной КС (`stations.at(src_id)`) вызывается метод `addConnection(dest_id, pipe_id)`, который добавляет запись в ее `outgoing_connections`.
5.  Если труба не найдена, пользователю предлагается создать новую.

### Топологическая сортировка (`topological_sort`)

Для анализа графа сети был реализован **алгоритм Кана** для топологической сортировки. Этот алгоритм позволяет линейно упорядочить вершины графа так, чтобы для любого ребра из `A` в `B` вершина `A` шла раньше `B`. Это возможно только для ациклических графов.

Алгоритм работает следующим образом:

1.  **Подсчет входящих степеней (`in_degree`):**
    *   Создается `std::map<int, int> in_degree`, где для каждой вершины (КС) будет храниться количество входящих в нее ребер.
    *   Программа итерируется по всем станциям и их исходящим соединениям. Для каждой станции, куда ведет ребро, счетчик `in_degree` увеличивается на 1.

2.  **Инициализация очереди:**
    *   Создается очередь `std::queue<int>`.
    *   В очередь добавляются все вершины, у которых входящая степень равна 0. Это "корневые" узлы, с которых можно начать обход.

3.  **Основной цикл:**
    *   Пока очередь не пуста, из нее извлекается вершина `u`.
    *   Вершина `u` добавляется в результирующий отсортированный список.
    *   Для каждой соседней вершины `v` (в которую ведет ребро из `u`):
        *   Входящая степень `in_degree[v]` уменьшается на 1 (так как мы "удалили" ребро из `u`).
        *   Если `in_degree[v]` стала равна 0, вершина `v` добавляется в очередь.

4.  **Проверка на циклы:**
    *   После завершения цикла, если размер результирующего списка меньше, чем общее количество станций в сети, это означает, что в графе есть цикл. В этом случае топологическая сортировка невозможна, о чем сообщается пользователю.
    *   В противном случае, отсортированный список выводится на экран.
